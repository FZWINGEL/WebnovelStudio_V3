# Model preferences and dispatch

The native header keeps the active model visible in Library and Workspace. Search and keyboard navigation browse the offline reference catalog; clicking a model, Enter, or Ctrl/Command+1–9 commits the choice. Favorites are stored independently. Settings contains supported reasoning and response-speed choices; traits do not appear inside model rows. Choosing Codex Luna initially selects Max and Fast (`priority`) from the verified reference options. Choosing an unavailable model remains an explicit saved preference and blocks generation. Manual writing stays available.

Rust owns app-local preferences in Library schema 2, separate from project schema 11. One strict `app_preferences` row stores a decimal revision and nonsecret JSON containing provider/model IDs, optional reasoning/service tier, and unique favorite keys. Schema 1 migrates transactionally. Writes compare the expected revision and reject unknown models, unsupported traits, malformed revisions, and duplicate favorites. Empty optional traits serialize as JSON null. There are no credentials, live discovery probes, or provider requests in this slice.

`provider_state` reads the confirmed settings, catalog, and dispatch readiness. `save_model_settings` stores and returns a confirmed state. The renderer makes no optimistic active-model change. A failed or uncertain write triggers one read of current settings, never an automatic replay. If that read fails, the active state becomes unavailable and new Send actions stay disabled until an explicit check succeeds.

Only the deterministic local test model can dispatch. The seven Codex entries are a dated reference catalog, with unavailable connections and unknown context/output limits. The reference options are not a claim of current discovery or of upstream execution settings. Existing mock byte accounting is not reused as a live model token limit.

At Send, the renderer freezes its selected model with the pending request. The IPC helper sends this selection separately from the existing core request so historical mock receipt payloads retain their exact hash contract. Rust serializes preference reads with new request acceptance, rejects every non-mock selection, and refuses a new mock request when the active choice has changed. An exact existing mock operation may still be checked after a preference change: Rust validates current project access, finds its operation in the current namespace, and the core verifies the immutable request payload before returning its receipt. A modified payload or a fresh operation cannot inherit that exception. No model change redirects an accepted request, changes its history, or reruns generation.

The temporary mock-only binding belongs to this slice. Enabling a live adapter requires an explicit provider/model/trait binding in immutable packet and run contracts, qualified budgeting, provider readiness, dispatch and Stop integration, and failure tests. Persisting a selection does not complete W8.
