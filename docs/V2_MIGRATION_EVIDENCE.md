**Inspected baseline:** V2 commit `c41c6e45c41cfdbcfcf51aa4840605efb4975845`, 5 September 2026. **Status:** verified source inventory and proposed import contracts; no V3 importer or actual-manuscript migration has been executed.

The [baseline CI](https://github.com/FZWINGEL/WebnovelStudio_V2/actions/runs/33963410139) passed on Windows and Ubuntu; its 169 unit/integration and five browser tests establish V2 fixture behavior, not V3 import correctness. ## 1. Schema detection and snapshot boundary

V2's baseline [schema.sql](https://github.com/FZWINGEL/WebnovelStudio_V2/blob/c41c6e45c41cfdbcfcf51aa4840605efb4975845/src/db/schema.sql) is not the complete current schema. [Eight ordered migrations](https://github.com/FZWINGEL/WebnovelStudio_V2/blob/c41c6e45c41cfdbcfcf51aa4840605efb4975845/src/db/migrations/index.ts) add revisions, working copies, runs, audits, settlement, option state, segments, and retirement. The [migration runner](https://github.com/FZWINGEL/WebnovelStudio_V2/blob/c41c6e45c41cfdbcfcf51aa4840605efb4975845/src/db/migration.runner.ts) uses `PRAGMA user_version` and transactional individual steps; `schema_migrations` also records migration names/versions.

The first supported import target should be a consistent schema-8 V2 snapshot validated against the actual tables/columns and relationships, not just an integer version. Earlier/incomplete/newer versions are unsupported until explicitly covered by another fixture. Do not run V2's application initializer against the source as an inspection shortcut: [startup](https://github.com/FZWINGEL/WebnovelStudio_V2/blob/c41c6e45c41cfdbcfcf51aa4840605efb4975845/src/db/client.ts) can migrate it and turn orphan queued/running jobs into interrupted records.

Prefer a V2-generated consistent backup. [V2 backup/restore](https://github.com/FZWINGEL/WebnovelStudio_V2/blob/c41c6e45c41cfdbcfcf51aa4840605efb4975845/src/core/studio/local-backup.ts) includes a `VACUUM INTO` snapshot helper, integrity/foreign-key/schema checks, staged restore, and pre-restore recovery. V3 uses its own read-only importer and recovered-copy policy; it does not port V2's in-place restore mechanism. Never copy only a live SQLite main file or open it with an unjustified `immutable` flag while V2 may write.

The snapshot can contain multiple V2 projects. Enumerate them read-only and let the author select which to import. Produce one independent V3 project per selected source project. Preserve source-project identity in the import manifest and validate every generic reference against that project; a project filter must not quietly discard a cross-project dangling reference.

## 3. Import behavior to specify in F1

1. Open only the consistent source snapshot read-only. Record importer version, schema fingerprint, source hash, selected source-project ID, and intended independent destination.
2. Read all relevant rows directly, including retired/superseded/stale history. Validate ownership and generic references before assigning V3 links; a SQLite foreign-key check alone is insufficient.
3. Convert prose with a versioned deterministic rule for paragraphs, blank lines, CRLF/LF, and Unicode. Preserve original narrative bytes separately and report projected differences. No Unicode normalization or automatic punctuation cleanup. Allocate V3 block IDs with a retained source mapping.
4. Preserve a present working copy exactly, including empty text. If it is NULL, report that no working copy existed and offer a visible initial-body choice or an empty document while keeping all drafts. Record the choice; do not silently substitute approved/newest prose.
5. Stage the entire new V3 project, allocate new identity and operation namespace, validate counts/hashes/relationships and backup recovery, then install it and register it. Copied legacy operation records are inert provenance, never active V3 receipts or resumable jobs.
6. Produce a reconciliation report with source/import counts, working/approved text comparisons, unmatched references, retired content, and limitations. Importing does not automatically activate V3 ready/story records.
7. On failure, keep V2 untouched and leave identifiable staging that can safely restart. Repeating the same source-project/fingerprint import detects the previous result; importing a changed source does not merge into an edited V3 project.

Preserve the original V2 snapshot at its source/backup location outside the portable V3 project. Do not copy its entire raw database into `legacy/`: it may contain unrelated projects or sensitive provider metadata. Apply the architecture's narrative/diagnostic allowlist, exclude credentials/environment/authorization data, and report any redaction. Exact narrative bytes and a source fingerprint can be retained without exporting unrelated secrets.
