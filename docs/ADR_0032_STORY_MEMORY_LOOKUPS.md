# ADR 0032: Model lookups over reviewed story memory

Status: implemented development slice. Extends C6's existing optional Working,
AuthorRoom, Discuss route; it does not enable restricted-writing lookup or
complete C5/C6 qualification.

## Author outcome and boundary

When an author enables **Look up story details when needed**, the assistant can
find reviewed character, topic, object and promise identities and read their
recorded histories. This connects the existing author-reviewed memory to the
bounded read loop. It does not require another review workflow, increase the
three-call allowance, change the selected writing model, or permit edits.

The Rust project owner loads one authenticated frozen snapshot. All results
come from its selected immutable possession, promise and knowledge sets, never
the current project catalog or current manuscript. Stored observations are not
exhaustive world truth. A belief is not a fact, an absent observation is not
unawareness, and an absent payoff is not proof that a promise is unresolved.

## Version and compatibility

Keep the provider envelope `story-lookup.v1` and its existing search/read
shapes. Add an application-owned optional field to `LookupPacketInput`:
`reviewedMemory: "reviewed-memory.v1"`. Fresh lookup discussions receive it;
every child retains exactly its root's capability. Absent legacy fields stay
absent through packet reconstruction, recovery and historical validation.

The original response instruction remains byte-for-byte unchanged when the
capability is absent. Only a packet carrying the capability receives the extra
tool instructions. New memory operations are refused without that capability,
including malformed responses, advance, packet validation and backup checks.
The user authorizes read access through the existing lookup choice; this field
is generated by Rust, not an additional renderer permission claim.

Schema 34 raises the reader floor without new tables: the existing immutable
JSON request/result and packet rows retain the new evidence. Older readers
cannot open projects containing operation kinds they cannot validate. Existing
historical packets, envelopes and hashes remain valid without rewriting them.

## Read operations

All operations retain a unique `id` within the existing 1–8 read envelope.
IDs use the existing opaque ASCII contract. `offset` defaults to zero and is
at most 100000; `limit` is required and ranges from 1 to 20. Neither field
changes the source basis. A small limit such as 6 is recommended in the model
instruction; full result envelopes count against the existing byte allowance.

```ts
type MemoryRead =
  | { id: string; kind: "findEntities"; entityKind: "character" | "topic" | "object" | "promise"; query: string; offset?: number; limit: number }
  | { id: string; kind: "knowledgeHistory"; characterId: string; topicId?: string; offset?: number; limit: number }
  | { id: string; kind: "promiseHistory"; promiseId: string; offset?: number; limit: number }
  | { id: string; kind: "possessionHistory"; objectId: string; offset?: number; limit: number };
```

Entity queries are nonblank and bounded by the existing 512-byte query limit.
Match case-insensitive literal substrings of explicit reviewed label variants;
do not merge equal labels or infer entity identity from prose. Character
choices include reviewed possession holders as well as knowledge characters.
Catalog entries carry `entity`, `labelVariants` and one exact `sourceHandle`/
`source` supporting that identity. Order entries by first frozen source order,
then stable record order, retaining distinct IDs with the same label.

Each result uses the matching `kind`. `findEntities` contains `entityKind`,
`query`, `entries`, `offset`, `totalMatches`, `nextOffset` and `incomplete: true`.
Each history result contains the existing typed `history` plus `offset`,
`totalObservations` and `nextOffset`. The history's observations are the selected
whole-record page; its label variants and uncertainty metadata describe the
complete eligible recorded history. `hasRecordedPayoff` likewise describes
recorded history, not necessarily the current page or established resolution.
The model must read further evidence before citing an observation absent from
the delivered page. Null `nextOffset` means no more recorded matches in this
snapshot; it never means exhaustive story coverage.

No observation, quote or statement is partially clipped. If required target,
instruction and lookup evidence do not fit, use the existing visible budget
failure. Do not silently omit a requested result or authorize another paid call
to repair it. Pagination is an explicit model read within the existing bounds.

## Validation, persistence and inspection

One pure memory-query module derives deterministic catalog/history pages from
the frozen reviewed records. Storage executes it after snapshot authentication;
the packet compiler independently recomputes it and compares complete typed
results. Every returned observation and catalog source must match a permitted
exact source read. Complete reviewed sets are checked even if only one page is
delivered. Child source-title projections include only exact sources returned
by successful lookup results, with no current title substitution.

The existing immutable read identity, request/result hashes, source/policy epoch
fences, operation claims, Stop, recovery and cumulative byte limits remain the
only execution protocol. No new job queue or provider framework is introduced.
Backup validation reproduces memory-query semantics from the retained snapshot;
rehashed altered results or a capability changed between calls are rejected.

The context inspector shows the requested query, returned names/observations,
recorded uncertainty, page coverage and links to exact source revisions. It
distinguishes prepared evidence, confirmed delivery and unconfirmed delivery
for the selected invocation. Reading history in the UI never sends a request
or changes the saved context packet. Unsupported providers and modes remain
unavailable; their capabilities are not implied by this protocol extension.

## Current implementation evidence — 6 September 2026

Schema 34 is implemented as the reviewed-memory reader floor. The existing
immutable lookup request, packet, invocation and read records are reused; no
new tables or provider framework are introduced. Fresh opt-in lookup packets
carry `reviewed-memory.v1`, and child packets retain the exact root value.
Legacy packets with the field absent retain their original instruction and
packet bytes through reconstruction, backup and recovery.

The four typed operations are implemented in the bounded Working, AuthorRoom,
Discuss loop: `findEntities`, `knowledgeHistory`, `promiseHistory`, and
`possessionHistory`. Rust executes them from the authenticated frozen reviewed
sets, rechecks complete typed results before persistence, and refuses memory
reads without the capability. Focused storage, packet, boundary, backup and
protocol tests pass, including legacy search/read replay, memory refusal with
durable failed-result retention, child capability retention, and rehashed
receipt rejection.

The synthetic native mock journey exercised all four operations across three
invocations and reopened without hidden lookup work. The explicit bounded live
qualification also passed its three synthetic groups with three live calls,
exact-source inspection, unchanged prose, settled cleanup and no page errors,
using the Luna/xhigh/priority route. Evidence is retained in
`.local/native-results/memory-lookup-mock/qualification.json` and
`.local/native-results/memory-lookup-live/qualification.json`; the live slice
brings the cumulative confirmed live-call count to 24. This remains bounded
development evidence: it does not establish narrative understanding,
exhaustive continuity, general provider support, or hosted, author-trial and
release qualification.

## Evidence boundary and remaining qualification

The implementation evidence above records the bounded protocol, storage,
native mock and live checks for this slice. The following remain the contract
for future extensions and broader qualification; they do not claim that the
full C5, C6 or V3 gates are closed.

- Strict new read shapes, malformed/duplicate keys, bounded IDs/query/page
  values, and refusal of memory operations without the frozen capability.
- Equal labels with distinct identities, cross-chapter label reuse, knowledge
  versus belief, payoff/setup and possession observations, zero-match and
  partial-page uncertainty, stable ordering and no current-catalog fallback.
- Exact source/quote and result replay checks, invalid private/foreign records,
  rehashed result/capability tampering, and unchanged legacy packet bytes.
- Durable expansion, Stop before another call, source/policy change, recovered
  history, lost acknowledgment and cumulative budget refusal without replay.
- Native catalog → history → answer inspection using synthetic records, plus
  a separately recorded bounded live Codex qualification on English material.
- No claim of general narrative understanding or complete continuity from a
  successful lookup fixture.
